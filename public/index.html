A Governed AI-Agent Platform, Built Solo

It started with one question: what does it take to let an LLM act inside an enterprise system without weakening the guarantees that make it enterprise-grade? Instead of guessing, I built the system and found out: a .NET 11 fleet where tool-calling agents run beside conventional business microservices under one .NET Aspire runtime.

I build it alone, with AI coding agents as my pair programmers. They write code fast, and they also drift. So I made the rules executable: every design decision is a written record, every rule that matters is a test that fails CI, and every bug fix ships with the test that would have caught it. The agents work inside those rails; the decisions stay mine.

The AI platform layer: decisions I would defend

  • Policy is the client, not a step developers remember. Every orchestrated model call goes through a governed Microsoft.Extensions.AI client (PII redaction, budget, rate limit, telemetry), and order matters: the tool loop and retries wrap around it, so each round trip and each retry is counted. A test asserts the order.
  • One budget ledger, because N replicas used to mean N budgets. Reserve before the call, commit the actual after it, release on failure, in one durable ledger shared by every service that spends tokens.
  • An evaluation loop that grades its own judge. An LLM judge that passes everything looks perfect, so calibration cases feed it known-wrong answers and only a parsed verdict counts as "caught". Held-out cases and repeated runs separate a real improvement from noise.
  • One seam to every model, one gateway for everyone else. Only one library may talk to a model provider; other services reach models through an OpenAI-compatible gateway as service accounts. GPU capacity is a fleet-wide lease in Redis: 1.2 ms per acquire and release, and 60 racing workers never held more than 3 slots.
  • A written answer to "what leaves this process?" One ledger lists every way data leaves a service on the AI side, with its guard and its test, and CI fails when a new path has no entry.
  • Security fails closed. An unconfigured control stops the service instead of letting requests through; agents get a code-owned set of capabilities and human approval that a database row can tighten but never loosen.

What building it taught me

  • Two correct components can make one wrong system. A route and its auth check disagreed about a path prefix. A smoke test caught it; now a rule keeps the two in one change.
  • Rules with no executor are only documentation. I once wrote that my tests ran on every build. There was no CI at all. Twenty lines of YAML fixed it, and since then every check must prove it actually scanned something.
  • Say what is not done. It has no paying users and has never run in production. I track its known gaps openly rather than present it as finished.
